# 两档网球视频制作耗时与质量复盘
日期：2026-09-09。审查快照：6fb3bbdc30e93eccb081aa30ad1cd138da7054bd。

本次完成生产记录、工作流、生成器和佩古拉正式文案审查；没有重剪、重推已发布视频，也没有完成性能代码改造或新速度基准测试。以下分清已发现问题和待实施措施。此前制作中，我反复补环境、在成片后修低成本输入错误、重复等待全量检查，明显增加了用户等待，这是执行问题。

## 2. 最应优先消除的返工

1. **低成本检查太晚。** 标题宽度、标签数量、轮次用语、已审字幕标记等错误到了成片或发布才暴露。应在下载、模型调用、配音和渲染之前调用同一套正式发布校验。封面先以实际裁切预览核对，环境先检查 ffmpeg、字体、浏览器和 Python 依赖。
2. **旧请求重建覆盖精修结果。** 当前 build_interview_request.py 的请求契约包含 cover/lead_in；契约变化会触发 pending，_build_one 重做转写翻译并写正式 spec、字幕和推广文案。快照提交已实际把采访 reviewed_dual_asr 改回 auto_pending、19.23秒 lead 改回29.78秒，并覆盖精修翻译。必须防止旧请求在自动任务中覆盖已确认修订。
3. **失败恢复范围太大。** 临时工作流缺依赖、模型输出枚举与名字格式不兼容，引发多次恢复；大体积源片/成片包被重复传输。格式兼容应在统一适配层完成，保留原始模型输出，不能把失败结论改成通过。
4. **重复全量检查。** 文案字段或局部封面修订不应反复运行全量仓库测试。共享代码修改按仓库规范做相关测试和一次全量；成片变化仍须检查最终媒体及证据绑定。
5. **缓存已有，复用边界仍不足。** match-reel 已有源片和TTS缓存，两档已有部分环境缓存。应复用并补齐，而不是再建一套平行系统。

## 3. 下一轮实施顺序与验收

| 优先级 | 改动 | 验收证据 |
|---|---|---|
| P0 | 统一前置输入/发布校验，复用现有规则 | 标题超限、6个标签、字幕未审核、错误时间窗在昂贵工作前失败 |
| P0 | 每个 slug 单写入者、revision、写入前比较起始 spec 哈希；已确认/已发布修订受保护 | 旧请求不能覆盖人工精修；明确新修订仍能执行 |
| P0 | 阶段事件计时，绑定 spec/film 哈希 | 分开显示准备、排队、源片、模型、TTS、渲染、QC、发布、失败重试及用户修订；并行耗时不累加为墙钟 |
| P1 | 固定生产环境；按内容哈希复用源、音频、转写、翻译和TTS | 相同输入不重复下载/转写；模型、提示词、文本或声音变化正确失效 |
| P1 | 局部恢复和增量渲染 | 改封面不重做ASR，改一句仅重做相关TTS/片段；推送失败只恢复发布；最终媒体重新绑定QC |
| P1 | 在依赖满足后并行处理事实核验、素材分析和封面候选 | 同一素材只处理一次，同一正式 spec 只有一个写入者 |

生产顺序：接收并记时 → 便宜预检 → 源片与证据准备 → 一次形成文案/镜头对照稿 → 文本和实际配音时长预检 → 渲染 → 最终媒体QC → 已授权的发布及回执记录。

失败只恢复受影响阶段。既不跳过事实和媒体检查，也不为了通知字段错误重做整部视频。

## 4. 赛场之上：专业解读与感染力一起提升

佩古拉正式 spec 的68.92–115.85秒片段长46.93秒，render记录对应配音43.344秒，占约92%。文案重复“球还在来回”“谁都不肯先松手”等，信息增量偏低。此结论来自文案与时长对照，本次没有重听整条成片。

每期先确定一个有证据的主张，用开局问题、关键变化、结果兑现串起来；选择2–3个确有画面支撑的关键机制，有多少证据讲多少，不能为凑数编战术。每个机制要交代：
- 比分和压力背景；
- 可观察的发球落点、接发站位、击球深度、变线、脚步或上网选择；
- 这一选择怎样限制对手、创造下一拍机会；
- 对应时间码，以及适用范围：这一分、这一盘或有统计支撑的全场趋势。

例如“一发率47%升至70%、次盘零双误”能说明发球稳定性变化；不能仅凭它认定改了抛球、增加外角发球或接管所有前三拍。技术成因须由视频或可靠采访支持。

配音稿和镜头表一次对齐：源时间码、画面动作、旁白、证据、现场声留白。用短句和具体动词，删除重复报局势和空泛励志。真实TTS时长出来后再锁定切点，不靠加速念完。关键击球和赢家反应留现场声；必要时用短暂停格或标记解释一个机制，避免遮挡球、球员和比分。

传播设计：开头快速给出真实冲突，正文解答，结尾兑现。情绪来自关键分、球员反应和清楚的因果，不靠夸张形容或猜测心理。封面承诺必须在正文兑现。以完播、分享、收藏等反馈检验，不能承诺“必爆”。

现有佩古拉 spec 把统计卡放在最终获胜段之前，与用户后续明确要求不同。已推送版本不改；新片必须完整获胜一分 → 庆祝/握手 → 全画布数据卡10秒 → 品牌收尾。卡片遵循用户参考图的整体比例与铺满画布要求，不能只放大字号。

来源：[正式文案和剪辑配置](https://github.com/robertyang87/tennislive/blob/6fb3bbdc30e93eccb081aa30ad1cd138da7054bd/specs/reels/pegula-usopen-2026-qf.json)。

## 5. 赛后开麦：让球员的话成为主角

- 冷开场今后默认目标8–12秒；完整获胜动作或必要语义确需更长时再延长，通常不超过15秒。此为新编辑默认值提案，不是声称现有工具已有硬限制，也不修改已推送19.23秒版本。
- 同场获胜画面简洁交代情境，尽快进入采访，避免长段赛事解说重复正文。
- 用真实、具有反差的原话形成传播点，保留问题背景、限定语、关键回答和必要上下文；不能拼接出相反意思。
- 英文原声与中文逐句对应；按意群断句，保留自然情绪。转写和翻译一次集中审核，修正后锁定版本。
- 技术解读优先来自球员对发球、接发、上网等的解释；若补充编辑解读，要与原话明确区分，不把推断塞进翻译，也不用旁白盖住球员。
- 完整采访是否精简正文取决于任务要求；不能为追求生产速度擅自删掉重要问答。

## 6. 速度目标与质量底线

当前记录没有证明10分钟可稳定交付。建议下一阶段对每档连续10条新片记录：
- 正常短官方源、可访问素材场景：请求至可审成片以10分钟为目标；初期观察P50≤10分钟、P90≤15分钟，发布用时另列且计入用户总等待。
- 冷缓存、下载故障和用户修订保留真实耗时与原因，既报告总体也分组，不能删掉慢样本。
- 首次制作通过率目标≥90%；零旧请求覆盖、零重复推送。
- 所有关键比分和事实有来源；战术主张有对应镜头或可靠证据；字幕忠实；关键结局完整；最终文件与QC一致。
- 超时及时给出具体卡点和恢复动作，不重置时钟，也不以删内容或跳过QC换达标。

这组目标需要实测验证。当前完成的是诊断和实施/验收方案，不能标记为“优化已完成”。
