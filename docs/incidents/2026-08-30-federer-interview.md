# 2026-08-30 费德勒名人堂《赛后开麦》事故复盘

## 结论

这不是一次单点渲染失败，而是封面视觉、转写质检、重渲调度、发布幂等和状态表述
连续失守。最直接的用户影响是：完整致辞虽然最终完成并由 PushPlus 接收，但错误
封面先被发布，修正版又被旧状态拦住，异常多次停在红灯或绿灯早退上，用户等待了
近一天并反复追问进度。

以后不能再把“工作流启动”“工作流绿色”“PushPlus 返回 200”当作任务完成。
完成必须由当前输入对应的成片、质量凭证和发布凭证共同证明；手机是否实际收到，
是另一层独立状态。

本次整改同时取消 DeepSeek 和 MiniMax 在这条生产链中的参与。翻译、画面判断、
封面选帧、异常复核与资源替换均由 Codex 直接完成；机器闸只使用可在本地重复执行
的确定性检查，不再依赖外部模型的可用性、自由格式回答或置信度自报。

## 本次产品合同

- 栏目：网球时差 · 赛后开麦。
- 内容：费德勒 2026 国际网球名人堂完整入选致辞。
- 不用冷开场，不加旁白，不调整原话顺序，直接全文翻译。
- 画面保留英文原声，正文逐条提供英文和中文字幕。
- 封面必须使用费德勒本人正面、清晰的胸像近景大图，并保留名人堂语境；全场广角
  或人物占比过小的画面，即使人物正确也不能通过。
- L0–L2 质检通过后自动推送微信，无需人工放行。
- 翻译、封面与成片质检不得调用 DeepSeek、MiniMax 或以它们的输出作为放行条件。

## 问题与根因

| 问题 | 直接原因 | 系统根因 |
|---|---|---|
| 封面不是费德勒或人物太远 | `frame_at=60` 实际切到台下；180 秒候选又是全场广角 | spec 的 `_why` 是自述，不是成片证据；L2 没把人物身份、正面近景和主体占比绑定到最终 poster 字节 |
| 请求和正式 spec 可能分叉 | 两处都保存 `opening`、`subject`、`cover.frame_at`，只改一处时旧 spec 仍被视为已处理 | 人工请求是否 pending 只看文件存在，不比较用户生产合同 |
| 修 spec 后没有自动重渲 | 调度器只要看见同 slug 的 `render.json` 就判已完成 | 已完成状态没有输入指纹，绿色旧产物遮住了新输入 |
| spec 改动不能立即叫醒调度 | workflow 没监听 `specs/interviews/*.json` | 触发源只覆盖请求和工具代码，遗漏正式生产输入 |
| ASR 停顿幻听导致整条红停 | 第二 ASR 在情绪停顿里识别出孤立词 | 质检能拦截，但缺少“定向复核—安全销账—自动续跑”的恢复状态 |
| 失败后恢复过慢 | 只有无 `render.json` 超过 3 小时才释放 | 用固定长窗口代替当前产物/输入证据，异常被当成终点 |
| 新成片没有重新推送 | 旧 `pushed.json` 按 slug 无条件防重 | 发布幂等键没有包含不可变成片指纹 |
| 可能推到非微信默认通道 | POST 未显式传 `channel` | 把账号后台默认值当成稳定合同 |
| 把平台接收说成微信送达 | `code=200` 和流水号被口头简称为“推送成功” | 平台 accepted 与手机 delivered 没有分层；PushPlus OpenAPI 查单还需要本仓库未配置的 `secretKey` 与 IP 白名单，现有 token 不能完成送达核验 |
| 修复过程多次停住 | 每次失败只报告状态，未继续寻找安全恢复路径 | 缺少按阶段分类、带重试预算和完成定义的自动恢复机制 |
| 发送失败后可能重复 POST | 网络断开或 5xx 不能证明 PushPlus 是否已经收单 | 把非幂等发布 POST 当成普通可重试请求，会让同一视频重复推送 |
| 同 slug Release 可能仍是旧片 | `gh release upload --clobber` 后只探固定公开 URL 的 200/206 | 固定 URL 的旧 CDN 缓存也能通过探活；没有核对当前 Release asset 的远端 digest，也没有把该证明持久绑定到 `render.json` |
| 视频只有顶栏小标题 | HEADA 显示体在最终编码中整行未形成像素；人物内容标题又被放进 38px HEADB | 测试只查 ASS 事件和 Style，没查编码后像素；典礼复用了比赛的“赛事大、内容小”语义 |
| 顶栏修文案后 HEADA 仍为 0 像素 | runner nightly 与本地 libass 对同一 ASS 的运行时布局/复位行为不同；仅凭现有 artifact 无法在碰撞、MarginV 与颜色复位间唯一归因 | 本地纯色短片没有覆盖真实源片滤镜路径；像素闸只在 28 分钟正文编码之后执行，发现得太晚 |
| 首轮新规格被 19 个中文断点拦截 | 逐条翻译修正了含义，但相邻 cue 仍在单字虚词后截断 | 人工语义审校没有在提交前复用生产 `zh_problems` 规则；生产闸正确 fail closed |
| 制作与质检受外部模型牵制 | 翻译、视觉判断或复核需要等待 DeepSeek/MiniMax 返回 | 外部模型有密钥、网络、超时和输出格式风险；自由格式判断也不能成为可重复的生产凭证 |

## 最终执行边界：Codex 直接制作，本地确定性 QA

- Codex 直接读取源视频和原声，完成全文翻译、字幕对齐、顶栏文案、封面候选比较、
  近景裁切、最终观看与资源替换，不再把任何制作步骤转交 DeepSeek 或 MiniMax。
- 本地 QA 只验证可机械复现的事实：输入与产物 SHA-256、音视频时长、分辨率、
  音轨存在性、字幕 cue 数量与顺序、ASS 两级标题、编码后标题像素、封面尺寸、
  裁切参数、主体占比、资源可访问性及 PushPlus 流水号。
- 人物身份、是否正面、是否清晰以及语境是否正确，由 Codex 对本地抽取的实际
  poster 和相邻源帧直接终审；结果绑定当前 `spec_sha256` 与 `poster_sha256`。
  `_why` 说明、外部模型评分和自报置信度都不能代替对最终资源的检查。
- 除官方源视频获取和 PushPlus 发布外，生产链不应因为第三方 AI 服务不可用而停止。
  所有放行证据都能在同一工作树用固定命令重新生成并得到一致结论。

## 已落地防线

### 当前输入与成片绑定

- 对有 `qc_attestation.json` 的新产物，只有
  `qc_attestation.spec_sha256 == 当前 spec SHA-256` 才算已渲染。
- 同 slug 的字幕、封面、空档销账或其他 spec 内容变化后，旧绿色
  `render.json` 不再遮住新输入，会重新进入 dispatch 候选。
- dispatch 状态新增每个 slug 的 `spec_sha256`。定时班次只会保护正在处理的
  同一份输入；状态指纹与当前 spec 不同时立即释放。
- 旧产物没有 QC 时继续按已渲染处理，避免规则上线即批量重跑 58 条历史采访。
- 自动调度 workflow 监听 `specs/interviews/*.json`，正式输入修改后立即运行，
  每 10 分钟的 schedule 只作为兜底。
- 无当前成片的自动释放窗口从 3 小时缩短为 60 分钟。59 分钟内保护正常长片，
  超窗后自动重投；同 slug concurrency 防止并行写同一产物目录。
- 人工请求与正式 spec 会比较人物身份、片头决定、封面时间点、顶栏层级和
  `push.auto` 等生产合同。两者只要漂移，就重新进入生成队列；说明文字和运营
  文案仍允许在正式 spec 中独立编辑，不会无故触发 28 分钟全文重转写。
- 指纹规则上线前已经发布、但旧 QC 与 spec 在同一次旧工作流中天生错位的产物，
  只按一份明确的迁移 SHA 豁免；以后 spec 再改一个字，豁免立即失效。这样既
  不重发旧内容，也不会永久掩盖未来修改。

### 发布幂等与通道

- 发布账本的权威键改为 `pushplus:<slug>:<film_sha256>`。
- 同一 film hash 已发送时继续防重；同 slug 产生新 film hash 时允许再次发布，
  并保留旧版与新版两次历史。
- PushPlus POST 显式写入 `channel=wechat`，不再继承后台默认通道。
- PushPlus 成功响应必须保存流水号，并在日志中写明实际请求通道。
- 同 slug 覆盖 Release 后，必须从 GitHub 当前 asset 元数据读取原生
  `sha256` digest，与 QC `film_sha256` 完全一致后才写 `render.json`；证明同时
  持久保存为 `release_asset_digest`，L3 发布闸再次复核。新推送的视频 URL 带
  film hash 查询参数，避免微信/CDN 继续命中旧资源缓存。

### 状态语义

统一使用下列两层状态，禁止混写：

- `platform accepted`：PushPlus 返回 `code=200` 和流水号，表示平台收下请求。
- `phone delivered`：用户在微信客户端实际看到消息，或未来有经过验证的投递回执。

因此：

> PushPlus accepted != 手机 delivered。

自动化当前只能证明第一层。没有手机确认时，不得回复“微信已经收到”或“手机已送达”。

### 顶栏两级标题与像素证明

- 名人堂入选致辞固定为 HEADA 大标题“人物 · 致辞类型”，HEADB 小标题“典礼名”；
  不再要求或伪造比赛对手、比分。
- 名人堂 HEADA 固定使用单一 Noto Sans CJK SC Regular 54px 白字 run，HEADB
  使用 Noto Sans CJK SC Regular 38px；每个 ASS run 都显式写入 `\fs`，不只依赖
  Style 默认值。54px Regular 尚需正式成功 artifact 裁决，不能提前写成“已证明”。
- 正文编码完成后、海报与最终拼接之前，自动抽取 0.5 秒帧的顶部 150px，分别
  检查 HEADA/HEADB 带区的浅色文字像素。品牌绿竖条不能冒充标题；任一行不足
  阈值就让 render fail closed，不能进入发布。
- HEADA 和 HEADB 使用不同 ASS layer，禁止 libass 把永久同屏的两行当作需要
  垂直避让的同层字幕；两行同时写入固定 `\an8\pos(...)`，不把最终位置交给
  runner 的 MarginV/collision 自由布局；HEADA 主文字显式写白，不只靠 `\r`
  清除前一段品牌绿。
- 全片编码前先用真实源片、同一 `filter_complex` 和同一 ASS 预烧 1 秒并执行同一
  像素闸；该预检通过后才允许启动长片编码。正文编码结束后仍保留第二次像素复核，
  防止只在完整产物路径出现的差异。
- 预烧同时捕获 ffmpeg/libass 的 verbose `fontselect`：顶栏必须实际落到 Noto CJK；
  出现 DejaVu 回退或 `failed to find any fallback with glyph` 立即失败。这样缺字
  方框即使产生足够浅色像素，也不能冒充中文标题。
- 第二次失败 artifact（run `33323079498`）证明：即使把 `\pos` 移到竖条前，
  HEADSUBJECT 仍是 0 像素，HEADB 为 2480；最终 ASS 与时长无误。artifact 证明
  “装饰竖条 run + 中途 `\r` + 粗体 run”这一组合两次失败，但不能唯一隔离其中
  哪个变量是 libass 触发点，也不能再归因于定位标签顺序。人物大标题一次移除这
  三个变量，改为单一 Noto Regular 可见 run（54px 白字），小标题
  同为 Noto Regular 38px；一条可信的 400→Noto 日志、无缺字日志和两个带区的
  真实像素共同构成发布证据。像素闸先报哪一行缺失，字体闸随后验证不是 tofu；
  两道都必须通过。

## 仍需保持的硬闸

- 封面验收必须绑定当前 `subject`、当前 poster 字节与当前 spec；人物错误、看不清、
  非正面或主体太小必须保持失败并由 Codex 重新选帧、裁切和替换资源，不得用
  `_why` 文本或外部模型评分自证，更不得把失败海报带入发布。当前费德勒候选已从
  广角 180 秒改为 200.6 秒正面镜头，并以 1.9 倍放大形成胸像近景封面。
- ASR 可疑空档不能为了赶进度直接放宽。Codex 必须回到实际源音频、波形和前后
  cue 复核，确定为无语音停顿后才写入 `caption_gaps_ok`；证据冲突时保持 waiting，
  输出具体区间和上下文，并在修正后自动从失败阶段续跑。
- PushPlus POST 已开始但没有回执时，发送结果不明。为避免重复消息，此状态只能
  标记 `uncertain` 并告警，不能盲目自动重发。
- 已拿到有效流水号但发布账本提交失败时，只允许补记账，禁止再次 POST。

### 失败续跑规则

1. 下载、探测、抽帧、编码等幂等本地步骤遇到临时失败时，在限定次数内自动重试；
   重试耗尽后保存阶段、输入指纹、错误和下一步，定时任务从该阶段继续。
2. 本地硬闸失败时，由 Codex 修正字幕、顶栏、封面或 spec 并替换资源；新的输入
   指纹必须自动重新 dispatch，不能被旧 `render.json` 或旧绿灯挡住。
3. PushPlus 发送 POST 每次发布意图只允许调用一次。连接中断、5xx、响应无法解析
   或 `code=200` 但缺少流水号时，统一记为 `uncertain`，禁止自动再次 POST。
4. 已取得流水号时，后续账本、marker 或 git 提交失败只补写记录；任何恢复流程
   都不得重新发送同一 `slug + film_sha256`。

## Definition of Done

以后同类《赛后开麦》只有同时满足以下条件才可宣布完成：

1. L0：Codex 已从官方源和实际画面确认内容类型、人物与典礼/比赛身份一致。
2. L1：Codex 直接完成全文翻译；本地验证英中 cue 按原话顺序一一对应，所有
   ASR 分歧和字幕空档都已回听源音频并显式销账。
3. L2：成片为 1080×1440，音画等长、非数字静音、字幕完整；顶栏大标题和小标题
