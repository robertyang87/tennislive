# 拉沃尔杯交付复盘与预防流程（2026-09-22）

本次复盘针对从成片到微信的交付过程。导入成功、工作流已派发和微信成功是不同状态，不能互相替代。

## 已确认的问题

1. **先在本地出片，之后才补接仓库流水线。** 已有视频、封面和研究资料，却没有同步完成仓库原生质检、Release、复制页及推送登记，导致“成片完成”被误当成接近完整交付。
2. **上传调用多次中断，早期缺少可靠的落盘检查点。** 恢复时无法仅凭会话判断哪些块已成功，进度被反复确认和重试拖慢。不能把原因归结为“大块不支持”：最终 **70 个、每块最多 3 MiB** 的 Git blob 已成功上传，并逐块记录 SHA。
3. **拼接后的 AAC 时间戳与长静音问题在原生成片质检中暴露。** 原版在 103、117、173、220、350 秒被检查到数字静音，不能凭此前局部抽查宣告最终合格。修复保留可追溯的时间映射，重新编码音视频并同步字幕时间轴后，原生 L2 才真实通过。
4. **状态沟通缺少执行证据。** 未启动的并行任务不应描述为“正在执行”，没有实际进度依据时不应承诺固定完成时间；反复回复状态也不能替代继续执行已授权任务。

## 本次已落地的修复

- 以修复版 SHA256 与字节数锁定交付对象：`84dbd0edc75a11a3940911405245b57f81cb54ecdbf6ff0566f0839af33d6bcd`，218276856 字节。
- 上传完成即将分块 SHA 写入检查点；导入时校验每块 Git blob SHA、长度及整片 SHA256。
- 在 runner 上重建后重新执行仓库原生 `check_reel_landed.py`，由检查器生成真实 attestation。
- 发布影片到 Release；用原生模板生成复制页与推送页；元数据落库后，通过原生发布门禁派发现有微信工作流。
- 保留发布账本预占、防重和结果登记。既有账本状态不明确时先核查，不能删标记强行重发。
- 校验分块可跨失败运行恢复；QC 前后记录、字幕来源、修复映射及视觉复核证据一并留存。

## 今后的默认流程

1. **开始就进入完整原生流水线。** 先确定 spec、素材、封面、文案和输出路径，复用既有“网球有故事”样板，避免做完本地成片后临时寻找发布通路。
2. **先质检，再上传。** 对最终实际文件执行原生 L2；媒体或字幕有变化，就更新关联时间轴并重跑受影响检查。未经实际执行不得填写 pass。
3. **按哈希绑定整套交付。** spec、字幕、影片、字节数和 attestation 对应同一版本。复制页标题、正文、封面及下载链接也必须指向该版本。
4. **长任务从第一次执行就带检查点。** 每块上传成功即落盘，恢复时核对已有 SHA；只补未完成部分。断开会话不应抹掉交付状态。
5. **同类失败有界诊断。** 同一操作连续失败两次，停止原样重试，缩成最小可验证步骤定位读取、编码、调用或远端响应层；只对已确认的瞬时错误做有限重试，记录错误和恢复点。
6. **并行分工明确。** 上传/发布、文案网页、质检可分别负责；质检通过之前不发布，最终整合者核对输入版本和唯一发布状态，避免多人重复发送。
7. **以真实回执结束。** 页面与视频可访问、原生推送步骤成功、实际 PushPlus 回执和持久登记相互吻合，才标记已发送。服务接收回执与终端送达若可分开查，应分别报告，不能把派发成功当作微信已收到。

这些措施减少可避免的返工和重复发送，不能保证 GitHub、网络或推送服务永不失败。发生外部异常时，应保留可恢复状态、明确阻塞环节及最后成功证据，而不是反复报一个未经验证的倒计时。
