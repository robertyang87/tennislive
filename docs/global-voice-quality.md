# 全栏目配音：语义、读音与实际成片验收

2026-10-19 账号所有者全局要求：配音须按语义安排重音与停顿，系统处理多音字，形成可执行的制作和验收流程。适用于“赛场之上”“赛后开麦”“网球有故事”及后续栏目的新增或主动修订配音。历史已发影片不因本规则自动重做、重发。

要求的对象是观众最终听到的声音。写了标点、填写了 `style`、通过 ASR 或保存了词边界，都不能单独证明表达已经生效。制作方完成内部检查，不把常规审音转交账号所有者逐句确认。本文件规定制作与验收要求；具体字段、工具能力和门禁以实际实现为准，未实现的能力不得宣称已经自动校验。

## 1. 先写能自然说出来的稿

- 事实、比分和人名先核实，再写口语稿。每句有明确主语、动作和结果，长句按意义拆开；将“然而”“但是”、比分和结论机械地逐字读快，不算有节奏。
- 先确定每段的表达目的：交代处境、解释打法、积累压力、转折或释放结果。重音落在本段真正新增的信息，如关键比分、否定、反转和比较对象；不要每句都用同一种上扬或每个词都强调。
- 标点服务于句法和呼吸。暂停不能切开人名、比分、固定词组或否定关系；不要为了压进时窗删掉必要停顿或突然提速。时窗不足先改稿、延长对应画面或调整剪辑。
- 情绪来自已经核实的比赛进程及真实反应。技术分析保持清楚，关键结果可以有力度，不能凭配音替球员编心理活动。

## 2. 合成前形成语义朗读计划

按旁白段记录原稿、要传达的意思、主要重音、语义停顿、语气和预期时长；同时保留字幕显示稿与实际送给 TTS 的文字。逐个列出人名、术语、比分、日期和有歧义的多音字 occurrence，写清词义与预期读音。记录能追到具体段落和词的位置，不能只留一份脱离本片文本的通用词表。

例如“首盘三比三。接下来，她连赢七局。”可在交代“三比三”后停顿，将“连赢七局”作为主要落点；不能读成“连赢七分”，也不能在“三比／三”中间停。最后是否成立，要核实际音频。

多音字以词义、词组及整句上下文判断，不做全局单字替换。至少主动检查下列常见字，其他有歧义的词同样处理：

| 字 | 词义及读音例子 |
| --- | --- |
| 重 | 重新、重来：chóng；重要、重压：zhòng |
| 发 | 发球、发挥：fā；头发：fà |
| 还 | 还在、还有：hái；还击、归还：huán |
| 长 | 长回合、长时间：cháng；成长、队长：zhǎng |
| 得 | 得分、赢得：dé；打得好：de；“这一局得守住”：děi |
| 行 | 行得通、继续前行：xíng；银行、行业：háng |
| 种 | 种子、一种：zhǒng；种下：zhòng |
| 落 | 落点、落败：luò；落下一个重要细节（遗漏）：là |

不能因“重新”的读音错了，就把所有“重”改成“虫”。优先改写为同义且自然的整句；需要精确纠音时，仅对已确认词义的词组或完整请求应用有边界的 TTS 输入修正，并保留显示文字、实际输入、预期读音和修改原因。字幕、封面及推送文案仍用规范汉字，不能把纠音用的同音字暴露给观众。

## 3. 先验证后端能力，再做少量样音

先核当前后端、具体音色和调用方式真正支持哪些能力：情绪风格、重音、停顿、语速、音高、SSML 或发音标注。供应商支持某功能，不代表选定音色、接口或本地封装已支持。

- 必需的朗读控制不受支持时，必须在批量合成前失败并说明原因。不能接受了参数却静默忽略，也不能把 SSML 当普通文字送入后端后声称已应用。
- 允许降级的可选控制，必须明确警告并记录实际采用的方法；经改写、标点或可用控制实现同一语义后，重新核听样音。警告不是表达合格的结论。
- 首轮只选少量代表句：开场、最强转折、一个高风险读音句及收尾；可由同一句覆盖多个目标。保持实际使用的后端、音色、语速和参数，验清方向再生成其余段落。
- 每份样音保留实际文字、参数、音频哈希与检查结论。样音中没有出现的词和段落仍未审；不能用一条合格样音覆盖全片。

## 4. 审查将进入影片的全部实际配音字节

完整合成后，为所有旁白、封面口播、数据卡及品牌片尾列出实际音频清单，绑定请求、文本、音色、参数和音频 SHA。审的是这些文件，不能播放另一份缓存或随后重新合成的声音来替代。

逐段检查漏字、添字、错读、词义、语义重音、停顿、句尾、情绪和可懂度；每个高风险词按清单核对。留真实方法、审查范围、问题所在时间或词位置、实际结论和证据。无法确认的段落或读音保留待审，不能填成“通过”。

证据的能力须区分清楚：

- ASR 可辅助定位漏词、重复或可疑片段；识别成规范文字仍可能把错误声调、重音或断句掩盖掉。
- WordBoundary/marks 可核对时间、覆盖及截断；它们不是音频里确实读出了该词的证明。
- F0、声学特征、音素比较及控制样本可支持具体读音的有限判断；不能据此自动认定整句自然、有感染力或全片已经听审。
- 完整听审须实际播放对应声音，逐段判断内容和表达。只有自动或有限声学检查时，明确记录其范围，不能标记成真人听审或“全片已听、全部多音字已正确”。

自动检查、有限证据、完整听审和尚未核实四种状态不能混写。缺少真实完整听审时，不以 ASR 全文一致、零报错或证据数量补成完整听审结论；仍按实际完成范围记录，未完成部分继续处理。

## 5. 失败只修相关请求，并检查改写的新风险

错读先回到词义和上下文，表达生硬先改句法和节奏。需要纠音时使用上文的有边界修正；需要风格控制时，先验证后端真实能力。每次只重做确实改变的请求，保留原问题及修复后的实际音频，不把失败记录改成从未失败。

改写后重新扫描整句：避开一个多音字，可能引入另一个多音字或改变比分、人物及因果。新增或改变的实际音频重新审查；其他请求只有文字、参数和音频字节仍严格相同，才可复用原有证据。声称修复必须对应修复后的声音，不以请求发出或返回成功代替。

## 6. 审完冻结，正式渲染严格复用

完成本期文案、朗读计划、问题闭环和实际音频审查后，冻结请求、实际音频、词边界、参数、实现版本与证据绑定。使用已有[原生配音小包机制](reel-frozen-tts-bundle.md)保留实际字节，正式渲染严格导入同一份小包；小包完整性通过只证明输入一致，不另授予读音或表达合格结论。

文案、音色、后端、声音参数、实际控制方式或相关合成实现变化后，按真实变化重新验证受影响输入。不能静默重合成并继承旧审音结论。仅调整取景或字幕位置且声音请求、字节和播放速度均未变时，可复用声音证据，仍须检查新的成片接缝与同步。

## 7. 最后验收实际成片的声音和接缝

以最终 MP4 的 SHA 为对象，检查实际导入的是已审声音，并听核所有配音段及其前后接缝：首字是否被切、句尾是否完整、必要停顿是否保留、时长是否挤压、与原声是否抢话、情绪是否突然断开、字幕是否对准。镜头时间或拼接方式改变后，不能只因独立 MP3 没变就跳过接缝检查。

关键原声和反应按已有完整窗口及双语字幕规则保留；我们的解释安排在合适空隙，不为了配音方便剪掉关键过程。普通原生赛场之上继续执行保留源片原声、去除自动增益/ducking/归一化的既有规则；本文件不恢复响度、幅值、阈值静音或源增益/PCM 检查。

验收记录绑定实际影片、实际声音清单和实际检查范围。问题未解决不能进入发布；已发布影片不因新增流程自动再次推送。每个后端能力、证据覆盖、冻结复用及发布条件的实现，都要有相应检查或明确的未实现状态，不能只靠文档声称守住。


## 8. 当前可执行门禁

共享工具是 `tools/voice_quality_gate.py`，只用标准库。它不合成、不下载、不把自动检查写成审听通过。下列命令中的目录必须是本期正常产线的真实产物目录，不能给示例文件补假哈希冒充成片。

```bash
# 正常封存 render_inputs 之前：读取真实小包，登记全部请求与实际音频。
PYTHONPATH=src:tools python tools/voice_quality_gate.py \
  --capture --outdir "$OUTDIR" --spec "$SPEC" --bundle "$TTS_BUNDLE"

# 正常产线写入 render_inputs 并完成 Release 元数据后：生成待审模板。
PYTHONPATH=src:tools python tools/voice_quality_gate.py \
  --prepare --outdir "$OUTDIR"

# 完成实际音频及实际成片审查后检查；任何缺审或失配退出 1。
PYTHONPATH=src:tools python tools/voice_quality_gate.py \
  --check --outdir "$OUTDIR"
```

`--capture` 只写 `voice_quality_inventory.json`，登记全部冻结请求以及本地原生 `voice_*.mp3` 和配对词边界。已有库存不同时拒绝覆盖。普通赛场之上带小包的正式渲染自动在 `render_inputs` 封存前调用同一库存函数，封存库存哈希。小包和中间 MP3 清理后，发布仍核对封存库存、实际包哈希、请求数及当前影片身份，不重新合成。

`--prepare` 生成 `voice_quality_review.json`，每条实际声音的 `phonetics` 与 `prosody` 均为 `pending`，实际成片 `film_review` 同样待审。只有确实完成对应声音的完整审查，才能如实填写 `full_audio_listening`、审查者、带时区时间、实际音频哈希及具体观察；成片还须填写实际影片哈希与全部配音及前后接缝的真实审查。工具不提供“自动全部通过”命令。相同音频字节的多处使用可以引用同一真实声音审查，但成片中每处接缝仍需核验。

`--check` 逐项核对完整覆盖、文本及完整参数、实际字节、当前 spec、库存封存、render 与 film 身份。缺项、待审、ASR/marks 冒充完整审听、换过声音、换过词边界、换过当前影片或未审实际成片，均拒绝发布。它验证记录完整性与绑定，不能证明有人填写的审听声明是真的，制作方仍须对真实审查负责。

两处视频发送入口 `tools/push_reel.py` 与 `tennislive publish pushplus` 在网络等待及发送前调用同一检查。图片内容包保留原流程。已有严格验证的“仅修改微信消息、原影片完全不变”修订沿用原发布身份，不要求为新规则重做旧片配音；修改配音或电影字节不属于该例外。

采访和代码脚本型解说若只有旧 `narration.json` 中的音色/语速摘要，不能当成全部实际请求证据。必须先在各自产线保留完整实际请求 sidecar 或原生小包、全部配音与品牌片尾，并正常封存库存和当前配方/影片身份；目前缺少这些证据时门禁会明确阻止推送，不从默认值猜参数，也不宣称这些旧产物已完成迁移。全局要求与统一发送门禁已覆盖它们，自动库存采集的原生支持以相应产线实际实现为准。

## 9. 2026-10-20：自动五项检查可以代替真人听审放行

账号所有者 2026-10-20：「配音检验能自动化么？如果要让我去听，一个是不一定及时（时间冲突），一个是我也不一定听的标准」，看过方案回「好的」。所以门禁多认一种放行方法 `automated_voice_suite`，出片时自动跑，不再等人听：

```bash
python tools/voice_auto_review.py --outdir "$OUTDIR" --bundle "$TTS_BUNDLE"   # match-reel render 那一趟自动跑
```

| 项 | 怎么查 | 什么时候红 |
| --- | --- | --- |
| 完整 | faster-whisper 把实际音频转回文字，按**拼音**和送进合成器的文字比；第一遍对不上用大一号模型复听 | 漏读／多读超过 1 个音节，或连续漏 2 个 |
| 多音字 | `measure_polyphone` 拿**实际音频**当原句，和同一把嗓子念的正确／错误读音同音字比那一个音节 | A 档（非默认读音、换句复核）量不出 correct 就红；B 档（重发还长得行种落 在默认读音上）高置信错读才红 |
| 停顿 | 合成器词边界：人名、比分内部停顿 | 超过 0.18 秒；切出已知假词 |
| 语速 | 每秒字数 | 超过 6.3 字／秒 |
| 整句 | spec 里相邻两段 | 一句话被拆进两段分开合成（`--dry-run` 就红） |

证据写进 `voice_auto_review.json`，放行记录 `voice_quality_review.json` 的方法写 `automated_voice_suite`、审查者写「自动检查，非真人听审」，并钉住证据文件的哈希；证据被改过、身份不是当前这一版、有一条没过，门禁都不认。真人听审（`full_audio_listening`）照旧认，同一版有真人记录时自动记录不覆盖它。

**它管不到的，照实写**：重音落点和整体自然度没有可靠的机器判据，靠写稿时的结构规则防（整句不拆段、语速上限、每段一个主要落点）；默认读音上的多音字只量点名的那几个字；接缝由出片的确定性闸覆盖（旁白超长编码前红、原声段与旁白段互斥），这一步没另听成片。账号所有者抽听发现问题，就补成一条新的自动检查。
