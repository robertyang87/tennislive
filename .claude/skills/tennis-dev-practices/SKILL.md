# tennis-dev-practices

> 从 `CLAUDE.md` 原样搬来，一个字没改。**规矩本身仍在 CLAUDE.md**，这里是撞上问题时才查的档案。

### ⚠️ 反向验证救回一条恒真的断言

给「即时赛果停掉」写测试时，第一版喂了一场 `conftest.make_match` 的默认比赛
进去，断言「选不出 result」——**绿的**。反向验证时把开关拧回 1 重新跑，
它**照样选不出来**：默认那场球 `hotspot_score` 只有 **49**，而门槛是 **50**，
差一分。也就是说那句断言恒真，**开关开着它也绿**。

补上 `rank`（59 分）之后才真正有意义：开关=1 选出 `('result', 'm1')`，
开关=0 什么都没有。

**判据自己也要有判据**：断言「某个东西不出现」之前，先证明它在正常情况下
会出现。这条测试现在多了一句 `assert hotspot_score(...) >= HOTSPOT_THRESHOLD`
把这个前提钉住。又一次「断言全绿不等于页面对」。


### 判据扫得太宽，一天之内犯了四次——三次是被自己的注释误伤

写「不碰产物的工作流不许把 output 拉下来」那条测试时，同一个形状连着踩：

| 扫什么 | 被误伤的 | 收窄成 |
|---|---|---|
| 工作流输入的旧默认值 | 注释里正写着 `伊埃拉 vs 郑钦文` 那个坑 | 先 `_yaml_only` 去掉整行注释 |
| `push-reel` 里不许出现 `ffmpeg` | 注释里写着「这里不装 ffmpeg」 | 同上 |
| checkout 有没有 `fetch-depth: 0` | 注释里写着「原来这儿写着 `fetch-depth: 0`」 | 同上 |
| 工作流碰不碰 `output/` | `ci.yml` 的 `paths-ignore: output/**` 是**触发条件**；`probe.yml` 写的是 **`probe-output/`** | 只看 `jobs:` 以后 + 词边界 `(?<![\w-])output/` |

**工作流和测试的注释正是这个仓库记教训的地方**，正文里必然写着当年那些错值。
连注释一起扫，「把坑记下来」会被判成「又踩了这个坑」。所以扫工作流一律先
`_yaml_only`。判据宁可窄，不可宽——**扩大化的判据不吭声**，它不会告诉你
「我拦错了」，只会让下一个人把对的写法改成错的。


### ⚠️ rebase 之后要重跑全量——你跑过的那棵树不是你要推的那棵树

2026-08-03 的红：`auto-push-reel.yml` 里写着 `git config user.name
"github-actions[bot]"`，而 main 上**当天新加**了一条判据要求所有工作流用
`Claude` / `noreply@anthropic.com`（不然 GitHub 标成 Unverified）。

我本地全量是绿的（1194 passed）——**因为那一趟跑在切到最新 main 之前**，
那时这条测试还不在树里。之后 rebase 到最新 main，多了 5 条测试、也多了这条
新判据，CI 于是 `1 failed, 1199 passed`。

- **判据是提交数**：本地 1194、CI 1199，**两个数对不上就说明跑的不是同一棵树**
- 这条和「本地装着不等于 CI 装着」是一家的：那条差在环境，这条差在**版本**
- 所以顺序是 **rebase → 跑全量 → 推**，不是「跑全量 → rebase → 推」。
  别在拿到绿灯之后再动树

⚠️ **顺带一个更贵的**：`git checkout -B <分支> origin/main` 会把分支指针挪到
origin/main，**分支上还没推的提交就此掉出来**（我今天用它 rebase，当场把刚做完
的工作从分支上抹掉了；幸好已经 push 过，从 `origin/<分支>` 取了回来）。
要 rebase 就 `git rebase origin/main`，别用 `checkout -B` 代替它——
和「反向验证不许用 `git checkout` 还原」是同一族：**这两条命令都以「重置」
为业，而被重置掉的东西不会有人通知你**。


### 测试自己也吃「本地装着不等于 CI 装着」

上面那条测试第一版写了 `import yaml`。沙箱里装着，全量 1013 绿；CI 上没有，
`ModuleNotFoundError`，整条 PR 红（run 30648727062）。**yaml 不在 pyproject
的任何一个 extra 里，全仓库也只有这一处 import。**

- 扫工作流一律**按文本切**（`_steps` / `_yaml_only` / `_checkout_block`），
  别为一条断言把 PyYAML 拖进依赖
- 判据落在 `test_测试里不许import没声明的包`：扫 **AST 里真正的 import**，
  每个顶层模块名必须是标准库、`pyproject` 声明过的依赖、或本仓库自己的模块。
  ⚠️ **别写成「不许 import yaml」**——第一版就是这么写的，结果被自己
  docstring 里那句「第一版真加了 `import yaml`」误伤，而且拦不住下一个包
- 反向验证过两次：塞回 `import yaml`、随便塞一个 `import boto3`，都红

这条和「加新能力就要同时改三处」是同一家的，只是这次出问题的是**测试**
而不是产品代码——沙箱越用越肥，测试的依赖面也会跟着悄悄变宽。


### ⚠️「一次成功率」要把「闸拦下来」和「真出错」分开数

不分开的话，**闸做得越好这个数字越难看**——每多一道前置检查，就多一条
「本来会在第 6 分钟出一条废片、现在在第 30 秒红掉」的 run，而按红/绿数它
和一次真崩溃一模一样。这个指标会**反过来奖励把闸拆掉**。

2026-08-02 那天 30 趟 match-reel：23 成功 / 5 失败 / 2 取消 = **77%**。
拆开之后完全是另一回事：

| run | 死在哪 | 到失败 | 哪一类 |
|---|---|---|---|
| 30754424718 | 第 23 步「写复制页」 | **0.6 分** | 推送元数据缺失——闸拦下（#150 已修） |
| 30753081477 | render 内 | 3.2 分 | 闸拦下 |
| 30741935272 | 第 21 步「cover」 | 3.2 分 | 调封面的快速迭代，**本来就该快失败** |
| 30752131692 | render | 3.9 分 | **真 bug**：封面溶解底料在委托链上掉队 |
| 30752134514 | render | 3.8 分 | 同一个 bug（已修） |

**真出错只有 2/30 = 6.7%，而且是同一个原因。** 其余三次是闸在干活，
其中一次只花了 36 秒——那正是上一节这套开关买来的东西。

所以复盘这条线的稳定性时，判据是**「有没有一条废片被发出去」**，
不是红绿比。红得早是收益，不是成本。


### 反向验证之后要清 `__pycache__`，还原可能是隐形的

钉 `FINAL_CRF` 那条测试做反向验证时踩的：`sed` 改成 `"23"` → 跑测试（红，对）→
`cp` 还原成 `"18"` → `grep` 确认磁盘上是 18 → 跑全量，**那条测试仍然红，报的是
「被改成了 23」**。

原因是 Python 判字节码缓存失效看的是 **(mtime, size)** 这一对：`"18"` 和 `"23"`
**字节数一样**，而 `sed` 和 `cp` 发生在**同一秒内**，两个判据都没变，于是它照旧
用了从 crf-23 编出来的 `.pyc`。

**它不吭声**——源码里明明写着 18，`grep` 也确认了，只有 `import` 出来才看得见：

```bash
PYTHONPATH=src:tools python3 -c "import build_match_reel as r; print(r.FINAL_CRF)"
# 磁盘 18，import 却给 23
```

所以：**改完源码要验的是 `import` 的结果，不是 `grep` 的结果**（和「判断译名改没改对，
直接调 `player_zh()`，别看文件内容」是同一条）。反向验证这类「改一下再改回来」的
操作，还原之后加一句 `find . -name __pycache__ -exec rm -rf {} +`。

#### ⚠️ 更阴的一种：连着做两次反向验证，它们会互相遮蔽

上面那条说的是「还原之后」。2026-08-02 又栽了一次，形状不同：**连着拆三道闸，
第二道报绿**——而拆掉一道安全闸还能通过，看上去就是「这条判据是恒真的」。

真相是那三次替换都写成了 `    if False:`，而被换掉的两行**字符数正好相同**：

    if not push_is_auto(copy_path):     ← 35 字符
    if (outdir / MARKER).is_file():     ← 35 字符

于是第二次改完的文件和第一次**字节数一模一样**，又在同一秒内，
`(mtime, size)` 两个判据都没变——第二趟用的是**第一趟编出来的 `.pyc`**，
那里面第一道闸是拆掉的、第二道闸是好的，所以它当然绿。

清掉 `__pycache__` 重跑，第二道当场红。所以：

- **每一次反向验证之间都要清**，不只是最后还原的时候
- 一道闸拆掉却还绿，**先怀疑缓存，再怀疑判据**——两者的表现完全一样，
  而「判据恒真」这个结论会让人把一条好测试删掉


### ⚠️⚠️ 跑一趟测试会改到**跟踪进仓库的数据**，而 stop hook 会催你把它推上去

2026-08-29 量出来的：`pytest tests/test_cli.py -k knowledge` 跑完（**5 passed**），
`git status` 里 `data/story_state.json` 就脏了——少掉一条 `__visual_backoff__`。
走的是 `cmd_knowledge` → `clear_visual_backoff()` 这条**真路**，而 `test_cli.py`
一处都没给 `STATE_PATH` 打过桩（`test_render.py` 每条都打了，所以它一直没事）。

⚠️ **三样叠在一起才是真正的危险，单看哪一样都像小事：**

| | |
|---|---|
| 测试**全绿** | 没有任何东西说它写了仓库里的文件 |
| 这个仓库的提交习惯是 `git add -A` | 副作用会顺着一次正常提交进去 |
| **stop hook 会主动催**「有未提交的改动，请提交并推送」 | 于是工具在推着你把它推上去 |

而被改掉的是**另一条线的账本**：`__visual_backoff__` 那几条是「这个选题的素材
预检刚失败过，三天内别再排它」（见上面无人值守那节的第 ④ 条），抹掉等于让那条线
明天再去撞同一堵墙；同一个文件里的 slug→日期是「这个选题发过没有」，抹掉就是
**同一条知识帖再发一遍**，而微信那条消息发出去收不回来。

收在 `tests/conftest.py` 的 autouse fixture `_isolate_story_state`（和
`_no_ambient_github_token` / `_isolate_tts_cache` 同一个形状）：每个测试各拿一份
`tmp_path` 里的副本。

- ⚠️ **要拷一份真的过去，不能指到一个空文件**：`published_topics()` 读的就是它，
  指空了「这个选题发过没有」会全部答成「没发过」——那比脏一个文件糟得多
- 判据 `test_跑测试不许改到仓库里那份选题账本` **不查「有没有打桩」**（换个写法
  就绕过去了），是**真调一次写入，然后看仓库里那份文件动没动**；另加一头
  「隔离要真的指到别处，而不是把写入整个掐掉」——只有前一头的话，一个
  `mark_story_used = lambda: None` 的 fixture 也能让它绿，而那会把这条判据
  和它要保护的行为一起废掉。两头分别反向验证过，各红在自己的断言行
- ⚠️ **判「脏没脏」之前先 `git checkout -- <那个文件>`**：我自己就把上一轮
  留下的脏当成了「这一轮又脏了」，据此以为修复没生效，多查了两轮。
  **查产物之前先把产物清干净**，不然量到的是上一次的残留


### 环境不用每次现配：`.claude/hooks/session-start.sh`

账号所有者 2026-08-05：「之前好像有好几次都要重新安装配置环境……**浪费了很多
时间**」。对的——容器每次是干净的，而下面那一节（「先装依赖，别把缺依赖当成
已知红」）说的那套，每个新会话都要重来一遍五到十分钟。

现在收成一个 SessionStart 钩子，装的东西**从 `ci.yml` 推**，判据在
`tests/test_session_start_hook.py`：沙箱不许装得比 CI 少（装少了的样子是
「本地跑不了 CI 能跑的测试」，然后那几条被读成「这里跑不了」）。

两个坑写在钩子的注释里，都是当天踩的：

- **`apt-get update` 必须排在 install 前面。** 镜像里的索引是构建时的，
  直接 install 会去取已经被删掉的旧版本，报的是 **404** 而不是「索引过期」
- **`--no-install-recommends` 不是洁癖。** ffmpeg 的 recommends 拖着一串
  VA-API 驱动，而那正是上面 404 的那两个包

⚠️ **而第一版的幂等检查被自己的管道废掉了**：

    fc-list | grep -qi "NotoSansCJK" || need_apt=1     # ← 匹配上了也算失败

`grep -q` 一命中就退出，`fc-list` 随即吃 SIGPIPE，管道退出码 **141**，
而 `set -o pipefail` 把它判成失败。于是「装好了」被读成「没装」。
**它错的方向是「白跑一次 apt」**——慢一点、不报错、永远没人发现。
和本文件里 `until ! pgrep -f 'X'` 会匹配到它自己是同一个形状：
**检查自己的机制把检查本身废掉了**。落成变量再 `case` 匹配，整条路上没有管道。

#### ⚠️ 顺带两条，都是 CI 替我逮到的（run 30971701644）

**① `.claude` 不在 `ci.yml` 的稀疏检出里，五条判据的主语在 CI 上不存在。**
和「测试不许拿 `output/` 当判据的主语——CI 上它不在」是同一条，只是换了个目录。
差别在于那次是**假绿**（`glob` 返回空列表，看起来像「没有成片」），这次是
**真红**——所以这次便宜得多。**加一个新目录当判据的主语时，先问它在不在 CI 的
检出里。**

**② `Path.is_file()` 会抛，不是只返回 False。** 它只吞 ENOENT / ENOTDIR /
EBADF / ELOOP 那几类，**不吞 EACCES**——而 runner 上跑测试的用户根本进不去
`/root`，于是探那个众所周知的 CA 路径时 `os.stat` 抛 `PermissionError`。

而这个探测排在 `main()` 的**第一行**，所以它一抛就是**每一次 CLI 调用都崩**：
整条 match-reel 会死在还没解析参数的时候。也就是说一个「本地跑得好好的」改动，
会在 runner 上打爆所有出片——**而本地永远复现不出来，因为沙箱里跑的是 root，
root 绕过权限检查**。判据因此不能靠 `chmod 000` 造场景（那样造出来的
「不可读」在这儿是可读的，测试会因为错误的原因变绿），要直接让 `is_file` 抛。

**探一个「众所周知的位置」失败就等于这台机器没有它**，任何 OSError 都一样——
这条路只是猜，猜不中是常态。显式配的那条不同：那儿配错了要报。


### 沙箱跑全量测试前先装依赖，别把缺依赖当成「已知红」

沙箱里全量跑常年 26 条红，我一直当成环境噪音，还在回复里写过「全是
`_cffi_backend` 缺失那一类」——**那句话是错的**。真去看每条的第一行错误，
是四种原因，只有最后一种被我说对了：

| 条数 | 报错 | 装什么 |
|---|---|---|
| 16 | `No module named 'rich'` | 主依赖，`pip install -e .` 就有 |
| 2 | `cv2 has no attribute 'CascadeClassifier'` | `visualqa` extra |
| 7 | `pyo3_runtime.PanicException` → `No module named '_cffi_backend'` | `pip install cffi` |
| 1 | `AssertionError: wqy-zenhei.ttc` | **真问题，见下** |

照 CI 那行装完（`ci.yml` 里就写着），26 → 1：

```bash
sudo apt-get install -y -qq fonts-noto-cjk        # ← 别漏，见下
pip install -q -e ".[dev,webrender,visualqa]" && pip install -q cffi
PYTHONPATH=src python3 -m pytest tests/ -q        # 907 passed, 0 skipped
```

**那 7 条 skip 也是缺依赖，不是「这里跑不了」。** 全是
`tests/test_collection_cover.py`——整个文件挂着
`skipif(not NotoSansCJK-Bold.ttc.exists())`。沙箱装的是文泉驿，
路径对不上就整file跳过，装上 `fonts-noto-cjk` 之后 7 条全绿。
CI 的 apt 那一步本来就装了它，我照抄 pip 那行时漏了 apt 那行。

**skip 和 fail 要一样对待**：一个常年不变的 skip 数字，和一个常年不变的
fail 数字一样，都是「没人真的看过」。`-rs` 一跑就知道为什么跳。

两条教训：

- **`opencv-python-headless` 不能不带版本装。** `pyproject.toml` 里钉着
  `>=4.10,<5`，我为了抽视频帧随手 `pip install opencv-python-headless`
  装到 **5.0.0**，`cv2.CascadeClassifier` 在 5.x 里没了——于是那两条红从
  「没装 cv2」变成「装错了 cv2」，长得一模一样。装 extra，别装包名
- **「一批红」要逐条看第一行错误。** 26 条里 25 条同因、1 条不同因，
  只看前几条就下结论，那一条就永远被埋在噪音里。这和「空结果先自证是真空」
  是同一个毛病：**一个笼统的解释盖住了一个具体的 bug**

那第 1 条是真的：`test_default_fonts_render_cjk_without_env` 里有一句
`any(tag in name for tag in ("Noto", "CJK", "SC"))`，拿**文件名**近似
「这是不是中文字体」。沙箱装的是文泉驿正黑（`wqy-zenhei.ttc`），中文渲染
完全正常，却因为名字里没那三个词被判红——**假阴性**。判据本来就在同一个
测试的下面两行（画出来比笔画：`render("网") != render("时")`，Latin-only
字体画出来两个豆腐块字节完全相同，反向验证过），把名字白名单删掉即可。

断言全绿不等于页面对。给推送加"可复制文案"时，`'长按下面整段' in body`、`'#网球时差' in body` 全过，人却没看过整页 —— 实际是同一份文案在推送里印了两遍，正文一遍、灰底复制块又一遍。截图一眼就看出来了。


### 加新能力就要同时改三处：代码、工作流的依赖、开跑前的预检

竖版剪辑那条线上，**同一类错误连着犯了三次**，每次都是「本地能跑，runner 上缺依赖」：

| | 缺的 | 因为加了什么 |
|---|---|---|
| 1 | `playwright` | 封面改成 HTML 渲染（为了和知识帖共用字体） |
| 2 | Chromium | 同上；而且我那个查找函数只按猜的路径 glob，**它其实装好了** |
| 3 | `cv2` | 跟踪裁切要 OpenCV 算帧差质心 |

三次**都死得很晚**：下完 64 MB 源片、合完原声、算完分段之后才报
`ModuleNotFoundError`，每次白跑一分半。而在沙箱里这些依赖恰好都装着，
所以本地怎么试都试不出来。

所以：

- **改代码的同一个提交里改工作流的依赖**。别指望「下次记得」——三次都是这么漏的
- **把依赖检查提到最前面**。用到什么就在开跑前 import 一次，不行立刻报，
  并说清两条出路（装依赖 / 关掉这个功能退回旧行为）。让失败发生在第 5 秒，
  不是第 90 秒
- **本地装着不等于 CI 装着**。沙箱是长期攒出来的环境，runner 每次都是干净的

同一条线上还有个双胞胎：**`-filter_complex` 的输出必须打标签并显式 `-map`**。
不打标签时 `-map 0:v:0` 取的是原始流，把整个滤镜图绕过去——裁切、缩放、跟踪
全部静默失效，成片直接是 16:9。**它不报错**，只是不生效，跟「补位的静音盖住
真音轨」是同一种毛病：**兜底和默认值出事的时候不吭声**。

#### 「三处」里，每个工作流各算一处

`test_ci装的字体覆盖代码要的每一个`：**不查「装了哪几个包」，查
「代码点名要的每一个包都在」**，以后往 `_FONT_FILES` 里加字体它会替你记得。

而工具 import `PIL` 和 `tennislive.render.webcards`（后者拖着
requests / rich / pypdf），跑到预检报 `No module named 'PIL'`。

### 开一条新线，先把阶段表画出来，再写第一行代码

账号所有者：「以后做一个新的项目，你就需要把前期、中期、后期的流程，分成不同的
任务／agent／子进程，都梳理清楚，而不是到做的时候才去想，然后缺什么。」

2026-08-01 那条新线的顺序正好是反的：我从「剪出来配字幕」开始，
**每失败一次往外长一截管线**——出片写完了才发现要转写校验，校验接好了才发现
要 cookie，成片进仓库了才发现推送这一段根本不存在，接上推送才发现**文案没有**。
七趟里六趟是在补一段本该在图纸上的东西。

**先画这张表。** 一行一个阶段，四列缺一不可：

| 阶段 | 做什么 | 跑在哪 | 要什么（依赖 / 输入 / 密钥） |
|---|---|---|---|

以「赛后开麦」为例，第一天就该长这样：

| 阶段 | 做什么 | 跑在哪 | 要什么 |
|---|---|---|---|
| 选材 | 找到那条集锦，定采访区间 | 本地 | 字幕接口、时长分布 |
| 转写 | 拉自动字幕 → 切行 | 本地 | yt-dlp、**字体**（要量行宽） |
| 校验 | 第二个源对一遍 | **runner** | 音频下载、whisper、**cookie** |
| 翻译 | 逐行中文 | 本地 | 译名表 |
| 出片 | 下源片 → 剪 → 烧字幕 → 封面 | **runner** | ffmpeg、**Chromium**、字体、cookie |
| 入库 | 提交成片 | runner | 写权限、**中间物清单** |
| 发布 | 复制页 → 提交 → 微信 | runner | PushPlus secret、Pages、**文案** |

画完它，三件事当场就掉出来了——**而我是分七趟撞出来的**：

- **依赖是按阶段列的，不是一张大清单。** 「出片要 Chromium」写在格子里，
  就不会出现「装了 playwright 忘了 Chromium」「装了三个包忘了项目自己」
- **哪几个阶段只能在 runner 上，一眼可见。** 那几个必须有本地替身
  （见下一节），否则每一个都要一趟五到十分钟的往返
- **「发布」是一个独立阶段，不是「出片」的尾巴。** 分开了才会想到
  `mode: push`（跳过重编码）和**文案这个输入**——文案是我在第八趟、
  接推送的时候才发现没有的

**落成代码就是 `--stage`。** `build_interview_clip.py` 现在有
`subs / sheet / verify / render`，工作流有 `mode: render|push`——这套划分是
对的，只是**我事后一段段补齐的**。先画表，这些 stage 就是照着表抄。

顺带：阶段表还回答了「这次失败该重跑哪一段」。今天多次整趟重来，
其实只有一个阶段变了。


### 失败在哪一段，就从哪一段接着跑

账号所有者：「有些非关键步骤失败了，不要从第一步开始再做，中间能否接上继续做，
你要有一定的判断。」

上一节那张阶段表，第二个用处就是这个：**它告诉你这次失败该重跑哪一段。**

2026-08-01 那趟推送在第 12 步「写复制页」失败（日期解不出来）。要重跑的

pip 35 秒、下 Chromium 60 秒、预检——**三分钟的准备，全是给出片用的**：
封面已经在仓库里、不转写、不下载、不编码，`push_reel.py` 只要 `requests`。

所以「接着跑」要落到两处，缺一不可：

- **阶段本身能单独跑**（`mode: render|push`）——这个我做了
- **每个阶段的准备也要跟着挑**。出片专用的依赖挂 `mode != 'push'`，
  另给一条一行的轻装步骤。**只挑工作不挑准备，等于没挑**——三分钟里
  真正干活的只有二十秒

判据落在 `test_只推送时不做出片那一堆准备`：凡是装/用 playwright、
faster-whisper、yt-dlp、ffmpeg、字体的步骤，都必须挂 `mode != 'push'`。

顺带一条判断力：**「重跑整趟」是最贵的一个键，却常常是最先按的那个。**
按之前先问一句——这次变的是哪一段？前面那些的产物还在不在？
（成片在仓库里、字幕在仓库里、转写报告在仓库里——大多数时候都还在。）


### 新接一条「只能在 runner 上跑」的线，先搭本地替身，再推第一次

### 查 PR 的 CI 别用 `get_status`：那张表在这个仓库恒空

`pull_request_read method=get_status` 查的是**老的 Commit Statuses API**，而这个
仓库的 CI 结果全在 **Check Runs** 里。于是它永远返回

    {"state": "pending", "total_count": 0}

——**和「CI 还没起来」长得一模一样**。PR #144 上量过：两个 run 10:19–10:20 就
`completed/success` 了，10:33 再查 `get_status` 仍然是 `pending / 0`。照它判会
一直等一个不会到来的绿灯，或者误报成还在跑。

判据要拿 run 本身：`actions_list method=list_workflow_runs resource_id=ci.yml`
按分支过滤，看 `status/conclusion`。⚠️ 它给每条 run 塞一整份 repository 元数据
（三条就 400 KB，直接超上下文），所以**落到文件再用脚本挑字段**，别直接读返回值。
⚠️ **`per_page` 对它没用**：2026-08-04 传 `per_page=2` 照样吐 **414,475 字符**。

又一次「空结果先自证是真空」，只是这次空的是查询用的那张表。

**轮询 CI 用 `get_check_run`，几百字节。** 三个接口的实测开销差了三个数量级：

| 接口 | 一次要多少 | 什么时候用 |
|---|---|---|
| `list_workflow_runs` | **400 KB+**（`per_page` 无效） | 只在**不知道 run id** 时用一次，落文件挑字段 |
| `list_workflow_jobs` | 几 KB | 要看**卡在哪一步**（带每步起止时刻） |
| **`get_check_run`**（要 `checkRunId`） | **几百字节** | **反复轮询「跑完没有」** |

`checkRunId` 从 `list_workflow_jobs` 的 `jobs[].id` 拿（那个 id 同时是
job id 和 check run id）。所以顺序是：列表拿一次 run id → jobs 拿一次
check run id → 之后一路 `get_check_run` 轮询。
⚠️ 参数名是 **`checkRunId`** 不是 `check_run_id`，写错只报一句
「owner, repo, and checkRunId are required」，看着像少传了 owner。

#### ⭐ 而「拿一次 run id」也不用付那 400 KB——按 `status` 过滤

上面那张表写着「只在不知道 run id 时用一次，落文件挑字段」，而**刚 dispatch
完要找的正是那一条在跑的**，它有一个天然的过滤条件：

    workflow_runs_filter: {"branch": "<分支>", "status": "in_progress"}
    → total_count: 1，**一条 run 的元数据，几 KB**

2026-09-01 实测：不带 `status` 是 19 条全量（`per_page=1` 照旧无效，
CLAUDE.md 早记过）；带上 `status=in_progress` 就只回那一条。

⚠️ **它只对「我刚点的那趟」成立**：并发跑着好几趟时同样会回好几条，
而且 run 一跑完这个过滤就查不到了（那时候该查的是 `conclusion`，
或者直接用已经拿到的 run id）。**别把它当成通用的「列出最近几趟」**——
那个还是得付全量。

### yt-dlp 的 `-o` 是模板不是保证

`bv*+ba` 合流时，如果最佳的那对不是目标容器装得下的编码（VP9 / Opus 之于
mp4），yt-dlp 会**自己改后缀**（`.mkv`）并 warn 一句——**而 `--no-warnings`
把那句吞掉了**。下游 ffmpeg 拿 `source.mp4` 去开，报 ENOENT。

**日志里只有一个退出码 254，但它自己就是判据**：`254 = -2 & 0xff`＝ENOENT。
同类：`ENOSPC` 是 `-28 & 0xff = 228`。ffmpeg 直接把 AVERROR 当退出码返回，
所以看见 200 以上的怪数字先按 `256 - n` 反解。

两层保险，都要出声（收在 `yt_download()`）：`--merge-output-format` 让它一律
remux；真落到别的后缀时**认出来按实际的用**，一个都没有时**把目录里有什么、
多大列出来**——只说「文件不存在」，下一个人还得自己去翻。

### 同一个常量赋两次，ruff 和测试都不吭声

改字幕版式时我在同一个模块里写了**两份** `_FONT_SIZE`（一份在量宽度那段，
一份在版式那段）。**行为碰巧是对的**——后定义的赢，而后定义的正好是新值。
但从那一刻起，改前面那份毫无反应。

- **`ruff --select F811` 拦不住**：它管重复 import 和函数重定义，
  **不管模块级变量重新赋值**
- **测试也拦不住**：跑出来的值是对的
- 它只在**下一个人改错地方**的时候发作，而那时线索早就凉了

判据只能自己扫（`test_字号只有一处出处`：`^<name> *=` 在模块里出现的次数
必须是 1）。同一族的还有「一个数写两处必分叉」——推送字段收到 `spec["push"]`、
栏目名收到 `column_of()`，都是这条。

### 顺手发现的无关问题：记下来，别在时效任务里展开修

「发现明确的问题就直接改掉，不用找我确认」这条规矩没有变——变的是**在赛果这
类时效任务中途撞上一个无关问题时，先掂量修复本身要不要再拖一轮验证**。判据
两条，占一条就该先记下来、等时效任务交付完再回头处理：

- **这个无关问题会不会拖慢当前这条时效任务的交付？** 会的话先记（写进
  `_note`、留一句 PR 描述或者单独起一个改动），赛果发完再修
- **修复本身要不要额外再等一轮全量才放心？** 要的话说明它不是"顺手"的规模，
  该单独处理，不该占用时效任务的窗口

真正"顺手"的规模是那种几秒钟能改完、一条目标测试就能钉住、不需要专门等一轮
全量的——本文件里那些"注释被误伤/判据扫得太宽"的修法大多是这个量级，那类才
配叫顺手。


### ⚠️ `until ! pgrep -f 'X'` 会匹配到它自己，于是永远退不出

2026-08-03 开了两个等 pytest 的循环：

    until ! pgrep -f 'pytest tests/'; do sleep 10; done

pytest 早跑完了，循环还在转——因为 **`pgrep -f` 扫的是整条命令行，而这个循环
自己的命令行里就写着 `pytest tests/`**，它把自己数了进去。

**它和「任务还在跑」长得一模一样**：没有输出、进程在、退出码没有。是清点残留
后台任务时才发现的。这跟本文件里那条「判据扫得太宽，被自己的注释误伤」是同一
个形状——**检查的范围把检查自己包进去了**。

- 等进程结束用 **PID**（`while kill -0 $PID 2>/dev/null; do …`），别用名字
- 非要按名字，就排除自己：`pgrep -f 'pytest tests/' | grep -v $$`，
  或者让被等的那条命令自己写一个完成标记文件，循环只看那个文件
- 更省事的是**让被等的命令自己在后台跑**（`run_in_background`），跑完自然
  有通知，不用另起一个循环去盯

**同一天的第二个变种：等待条件被当前状态自己满足了。** 等新产物落库时写的是

    until git log --oneline origin/main -1 | grep -q 'special-exempt'; do …

——而**当时的 HEAD 就是上一版 special-exempt 的提交**，条件一上来就为真，循环
立刻退出，看起来像「已经好了」。

**等「新东西出现」要比变化量（SHA、条数、时间戳），别比内容特征**——
特征往往当前就成立。这两条和「判据扫得太宽，被自己的注释误伤」是一家的：
**检查把它想排除的东西包进了自己的范围。**


### ⚠️ `read -t N -u 3 3</dev/null` 一秒都不等——我据此报了个错结论

同一天，等这条 run 的时候踩的。沙箱里前台 `sleep` 是禁的，我拿这个当替身：

    for i in $(seq 1 40); do 检查一下; read -t 15 -u 3 3</dev/null || true; done

**`/dev/null` 是立刻 EOF**，所以 `read` 立刻返回失败，`|| true` 把它吞掉——
四十轮在几毫秒里跑完，而它打印出来的是「poll-done after 40 rounds」，
**和真等了十分钟一模一样**。

代价不是慢，是**一个错结论**：我据此认为「十分钟了产物还没落库」，去查
`list_workflow_jobs` 看到步骤 5 在跑，就报给账号所有者「这一步已经跑了 11
分钟，job 超时 20 分钟」——**而那一刻它才开跑一分半，两分钟后就成功了**。

- 这和 `until ! pgrep -f 'X'` 会匹配到它自己是同一族：**用来等待的那个机制
  自己失效了，而失效的样子和正常一模一样**
- **等待要拿一个会前进的量自证**：循环里打印 `date`，或者比对开始和结束的
  时间戳。我那条循环末尾其实打了 `date -u`，只是**打在循环外面**——
  打在里面第一轮就露馅了
- 更省事的还是让被等的东西自己在后台跑完通知（`run_in_background`），
  别自己搓等待原语
